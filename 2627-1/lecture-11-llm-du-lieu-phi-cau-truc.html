1.
Dữ liệu phi cấu trúc

Cột "khó nhằn" nhất trong bảng thường là cột chứa văn bản tự do.

1.1. Một cột không giống các cột còn lại

Bảng reviews của Inside Airbnb (Santiago, 690 nghìn dòng):


reviews = pd.read_csv("reviews.csv.gz")
reviews[["listing_id", "date", "comments"]].head(3)

date lọc được, listing_id join được — còn comments thì groupby kiểu gì?

1.2. Câu hỏi thật mà bảng này phải trả lời

Đặt hàng từ bên liên quan
"Trong 2.000 review gần nhất, khách chê điều gì nhiều nhất — và khu vực nào bị chê về độ ồn nhiều nhất?"

Không có cột complaint nào để value_counts() cả. Câu trả lời nằm bên trong văn bản.

1.5. Bài toán của hôm nay

Với mỗi review, điền được một dòng như thế này:

Có bảng này rồi thì câu hỏi ở 1.2 chỉ còn là một groupby.

2.
Baseline không cần LLM

Trước khi vác búa tạ, thử cái tua vít đã có trong túi từ buổi 7.

2.1. Khía cạnh bằng từ khoá

Mỗi khía cạnh một bộ từ khoá, quét bằng str.contains:


KEYWORDS = {
    "noise": r"noisy|noise|loud|ruido",
    "cleanliness": r"clean|dirty|limpio|sucio",
}
for aspect, pat in KEYWORDS.items():
    reviews[aspect] = reviews["comments"].str.contains(
        pat, case=False, regex=True)

reviews[["noise", "cleanliness"]].mean()
            

noise          0.081
cleanliness    0.412

Ba dòng code, chạy 690 nghìn review trong vài giây.

2.2. Cảm xúc bằng từ điển

Đếm từ tích cực trừ từ tiêu cực — thô nhưng có ngay con số:


POS = r"great|perfect|excellent|excelente"
NEG = r"bad|dirty|noisy|terrible|malo"

score = (reviews["comments"].str.count(POS, flags=re.I)
       - reviews["comments"].str.count(NEG, flags=re.I))
reviews["baseline_sent"] = np.select(
    [score > 0, score < 0], ["positive", "negative"], "mixed")

Từ điển "xịn" hơn (VADER…) cũng cùng nguyên lý — vẫn là đếm từ.

2.3. Baseline giỏi gì, thua gì?

Giỏi

  • Nhanh: cả bảng trong vài giây.
  • Miễn phí, chạy lại ra đúng kết quả cũ.
  • Giải thích được từng kết quả.

Thua

  • "not clean at all" → dính từ khoá clean.
  • Mỗi ngôn ngữ phải soạn lại từ khoá.
  • Mỉa mai, viết tắt, sai chính tả: chịu.

2.4. Baseline không phải để thắng

Điểm chốt Baseline là thước đo: không có nó, bạn không thể nói LLM "đáng tiền" hay không.

Kỷ luật của người làm dữ liệu: baseline trước, công cụ đắt sau — và cả hai cùng được đo trên một bộ đánh giá (phần 5).

3.
Gọi LLM từ Python

LLM "đọc hiểu" được văn bản — và gọi được từ code, như mọi API buổi 6.

3.1. Chat và API là hai cách dùng một mô hình

Giao diện chat

  • Người gõ, người đọc.
  • Tốt cho khám phá, hỏi đáp.
  • Không lặp lại được 2.000 lần.

Gọi qua API

  • Code gửi request, nhận response.
  • Nằm trong pipeline, chạy hàng loạt.
  • Cách dùng của môn này (và của BTL).

3.2. Gemini API — LLM miễn phí cho môn này

  • Lấy API key ở Google AI Studio (aistudio.google.com) — free tier, không cần thẻ.
  • Model dùng trong môn:
Model Hợp với Giá trả phí (1M token vào/ra)
gemini-3.1-flash-lite trích xuất hàng loạt — quota free cao $0.25 / $1.50
gemini-3.5-flash văn bản khó, cần suy luận $1.50 / $9.00

Free tier: hạn mức theo ngày/phút — xem con số hiện hành trong AI Studio (mục Rate limits); thay đổi thường xuyên.

3.3. API key là mật khẩu


from google.colab import userdata   # Colab: menu 🔑 Secrets
API_KEY = userdata.get("GEMINI_API_KEY")
Cẩn thận Không viết key thẳng vào code, không commit lên GitHub, không dán vào chat/ảnh chụp màn hình. Lộ key = người khác tiêu quota (hoặc tiền) của bạn.

3.4. Lần gọi đầu tiên


from google import genai

client = genai.Client(api_key=API_KEY)
interaction = client.interactions.create(
    model="gemini-3.1-flash-lite",
    input="Chào bằng đúng 5 từ tiếng Việt.",
)
print(interaction.output_text)
            

Chào bạn, rất vui gặp!

Một request — một response. Giống requests.get() buổi 6, chỉ khác là server bên kia… biết đọc.

3.5. Prompt = hướng dẫn + dữ liệu


review = reviews.loc[7, "comments"]

prompt = f"""Bạn là công cụ phân tích review chỗ ở.
Review sau khen gì, chê gì? Trả lời ngắn gọn.

Review: {review}"""

out = client.interactions.create(
    model="gemini-3.1-flash-lite", input=prompt)
print(out.output_text)
            

Khen: vị trí trung tâm, chủ nhà thân thiện.
Chê: về đêm khá ồn do gần quán bar.

3.6. Nhưng… văn xuôi thì đưa vào bảng kiểu gì?

Chạy lại 3 lần, nhận 3 kiểu trả lời:


Lần 1: "Khen: vị trí. Chê: tiếng ồn."
Lần 2: "Khách hài lòng về vị trí nhưng phàn nàn về độ ồn."
Lần 3: "- Ưu điểm: location\n- Nhược: noise (ban đêm)"

Nội dung đúng cả 3 — nhưng không parse nổi thành cột. Ta cần ép mô hình trả lời theo mẫu cố định → phần 4.

4.
Structured output
& chạy hàng loạt

Bắt LLM điền form thay vì viết văn.

4.1. Khai mẫu trả lời bằng Pydantic

Mô tả "form" mà mô hình phải điền — kiểu dữ liệu + tập giá trị được phép:


from pydantic import BaseModel
from typing import Literal

Aspect = Literal["location", "cleanliness", "host",
                 "value", "noise", "amenities"]

class ReviewInfo(BaseModel):
    sentiment: Literal["positive", "mixed", "negative"]
    aspects_positive: list[Aspect]
    aspects_negative: list[Aspect]
    language: str          # mã ISO: "en", "es", ...

Literal = enum: ngoài danh sách này là không hợp lệ.

4.2. Truyền schema vào lời gọi


out = client.interactions.create(
    model="gemini-3.1-flash-lite",
    input=f"Phân tích review chỗ ở sau.\n\nReview: {review}",
    response_format={
        "type": "text",
        "mime_type": "application/json",
        "schema": ReviewInfo.model_json_schema(),
    },
)
info = ReviewInfo.model_validate_json(out.output_text)
info.aspects_negative
            

['noise']

JSON vào, object ra — model_validate_json vừa parse vừa kiểm tra kiểu.

4.3. Schema + enum: hàng rào đầu tiên

  • Model bịa nhãn mới ("wifi_speed") → validation từ chối, không lọt vào bảng.
  • Thiếu trường, sai kiểu → lỗi ngay tại chỗ, không âm thầm thành NaN.
Điểm chốt Ràng buộc trước (schema, enum) rẻ hơn nhiều so với dọn rác sau. Đây chính là tư duy QA của buổi 10 áp cho output của LLM.

4.4. Chạy hàng loạt: vòng lặp có kỷ luật


import time

results = {}
for rid, text in sample["comments"].items():
    try:
        out = call_llm(text)              # hàm gói lời gọi ở 4.2
        results[rid] = ReviewInfo.model_validate_json(
            out.output_text)
    except Exception as e:
        results[rid] = None               # ghi lại, xử lý sau
    time.sleep(4)                          # tôn trọng rate limit!

Free tier giới hạn số request mỗi phút — thiếu sleep là dính lỗi 429 giữa chừng.

4.5. Cache: đã gọi thì không gọi lại


CACHE = Path("llm_cache.json")
cache = json.loads(CACHE.read_text()) if CACHE.exists() else {}

def extract(rid, text):
    if str(rid) not in cache:              # chỉ gọi khi chưa có
        cache[str(rid)] = call_llm(text).output_text
        CACHE.write_text(json.dumps(cache))
    return ReviewInfo.model_validate_json(cache[str(rid)])
  • Tiết kiệm quota; chạy lại notebook không tốn request nào.
  • BTL: người chấm chạy pipeline với --skip-llm — đọc cache, không cần API key.

5.
Đánh giá, chi phí
& cạm bẫy

"Trông có vẻ đúng" chưa phải là đúng.

5.1. Hallucination có thật

Những lỗi chúng tôi gặp thật khi soạn bài này:

  • Review chỉ khen vị trí — model trả thêm cleanliness vào danh sách khen.
  • Review 4 từ — model "suy ra" cả cảm xúc lẫn 3 khía cạnh.
  • Review tiếng Tây Ban Nha — nhãn ngôn ngữ trả về "pt".
Cẩn thận Output của LLM luôn trôi chảy và tự tin — kể cả khi sai. Độ mượt không phải bằng chứng của độ đúng.

5.2. Bộ đánh giá: ~100 nhãn gán tay

  1. Rút ~100 review (ngẫu nhiên, đủ các ngôn ngữ chính).
  2. Cả nhóm tự đọc, tự gán nhãn theo đúng schema; bất đồng thì thảo luận, chốt hướng dẫn gán.
  3. Chạy LLM và baseline trên đúng 100 review đó — so với nhãn tay.
Điểm chốt 100 nhãn tay là "bộ test" của dữ liệu — không có nó, mọi nhận xét chất lượng chỉ là cảm giác.

5.3. Đo xong mới biết ai hơn ai — và hơn ở đâu

Kết quả minh hoạ trên 100 nhãn tay (notebook hôm nay làm bản nhỏ hơn):

Cảm xúc (accuracy) Khía cạnh (F1) Ngôn ngữ (accuracy)
Baseline từ khoá 0.62 0.48 0.71
LLM (flash-lite) 0.89 0.81 0.97

Chênh lệch lớn nhất nằm ở đâu (phủ định, đa ngôn ngữ…) → đó chính là phần "đáng tiền" của LLM.

5.4. Nhìn vào chỗ sai, không chỉ nhìn con số

  • Liệt kê các review LLM gán sai → có kiểu lỗi chung không? (review dài? mỉa mai? một ngôn ngữ cụ thể?)
  • Sửa prompt hoặc enum theo kiểu lỗi tìm được → đo lại trên đúng bộ 100.
Cách làm tốt Vòng lặp: đo → xem lỗi → sửa prompt/schema → đo lại. Mỗi thay đổi prompt đều phải qua "bộ test", như sửa code phải chạy lại test.

5.5. Chi phí tính bằng token

Mỗi interaction trả về số token đã dùng:


out.usage.total_input_tokens, out.usage.total_output_tokens
            

(182, 47)

Ước tính cho 100.000 review (~200 token/lượt vào, ~50 ra) với flash-lite ($0.25 / $1.50 mỗi 1M token):

20M token vào ≈ $5  +  5M token ra ≈ $7.5 → ~$12.5

Free tier đủ cho mẫu vài nghìn review (chạy rải ngày) — đủ cho BTL nếu biết chọn mẫu + cache.

5.6. Khi nào dùng gì?

Tình huống Công cụ hợp lý
Pattern rõ ràng (mã bưu điện, giá, ngày…) regex — buổi 7
Ngữ nghĩa, đa ngôn ngữ, quy mô vừa LLM + schema + bộ nhãn tay
Quyết định hệ trọng từng ca (pháp lý, y tế…) người thật đọc — LLM chỉ hỗ trợ lọc

Và luôn hỏi: sai 10% thì phân tích của mình còn đứng vững không?

Tổng kết

  • Dữ liệu phi cấu trúc: đổi dạng thành bảng rồi mới phân tích.
  • Baseline trước, LLM sau — cả hai cùng đo trên một bộ nhãn tay.
  • Pipeline LLM tử tế = schema + enum + rate limit + cache.
  • Chất lượng đo bằng nhãn tay, chi phí đo bằng token — không đo thì không kết luận.
